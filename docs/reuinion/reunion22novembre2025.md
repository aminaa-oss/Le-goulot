# Plan de réunion – Organisation du travail pour le projet *Le-goulot*

## 1. Modalités de fonctionnement et d’organisation du travail

### 1.1 Rôles et responsabilités
- Définition des rôles principaux (Product Owner, développeur·se·s, testeur·se, designer, responsable documentation…)
- Attribution des responsabilités :
  - Création et gestion des issues
  - Revue des Pull Requests
  - Gestion de la documentation (README, wiki, dossier `docs/`)
  - Gestion de la stratégie de version et des releases

### 1.2 Méthodologie de travail
- Choix du workflow Git (Git flow, trunk-based, feature branches)
- Gestion des branches et conventions de nommage
- Pull Requests :
  - Process de revue de code
  - Règles de validation (lint, tests, CI)
- Issues :
  - Définition des labels
  - Priorisation
  - Utilisation de GitHub Projects (tableaux, automatisations)
- Automatisation (CI/CD, GitHub Actions)

### 1.3 Communication
- Fréquence des réunions (hebdo/bihebdo)
- Outils de communication (Slack, Discord, GitHub Discussions…)
- Mise à jour du statut du projet via GitHub Projects
- Règles de feedback en revue de code

### 1.4 Documentation
- Structure du README : description, installation, usage, contribution, roadmap
- Mise à jour régulière de la documentation
- Utilisation d’un wiki ou d’un dossier `docs/` pour les contenus détaillés

### 1.5 Qualité du code
- Normes de codage, linters et formateurs
- Tests unitaires et d’intégration (outils, couverture minimale)
- Gestion et réduction de la dette technique

### 1.6 Gestion des versions et releases
- Fréquence des releases
- Convention de versionnage (ex : Semantic Versioning)
- Processus de build / packaging (si nécessaire)

---

## 2. Aperçu prévisionnel de la planification (Roadmap)

| **Phase** | **Objectifs principaux** | **Durée estimée** |
|----------|--------------------------|-------------------|
| **Phase 0 – Initialisation** | Mise en place du dépôt, définition des rôles, configuration de GitHub Project | 1 semaine |
| **Phase 1 – Architecture & Design** | Architecture du code, design initial, documentation | 2–3 semaines |
| **Phase 2 – Développement MVP** | Développement des fonctionnalités de base, tests initiaux | 4–6 semaines |
| **Phase 3 – Tests & Validation** | Tests, corrections, amélioration qualité | 2–3 semaines |
| **Phase 4 – Première Release** | Préparation de la version 1.0 (ou bêta), changelog | 1 semaine |
| **Phase 5 – Feedback & Itérations** | Recueil de retours, création de nouvelles issues, ajustement roadmap | 3–4 semaines |
| **Phase 6 – Fonctionnalités avancées** | Ajouts, performance, CI/CD avancée | Variable |

---

## 3. Suivi & adaptation
- Revues régulières de la roadmap (à chaque sprint ou milestone)
- Mesure des indicateurs de progression : issues fermées, couverture de tests, fréquence de release, qualité du code
- Réévaluation des rôles et besoins en ressources
- Début de projet, collaboration future
